# Learning Protocol

> 本文件定义本项目的学习方法论,所有后续学习都以本协议为准。
> 来源:`project-driven-framework-learning` Skill,针对 Electron + 用户背景(2 年 React/Next.js/Taro 经验)做适配。

## 学习目标(四个一级能力,优先级从高到低)

1. **架构设计** —— 模块边界、数据流、生命周期、扩展方式、规模增长后的架构演进
2. **重点基础** —— 只学真正决定工程能力的基础(进程模型/IPC/生命周期/安全配置),不背 API
3. **Bug / 安全 / 边界** —— 高频 Bug、生命周期错误、异步错误、内存泄漏、安全风险、生产环境差异
4. **性能与工程优化** —— 启动、CPU、内存、IPC、打包、日志、崩溃、可维护性

## 教学循环(每个功能必须走完)

```
需求 → 架构思考 → 用户回答 → 纠正理解 → 学习核心原理 → 最小实现 → 测试 → Bug 分析 → 性能分析 → 复盘 → 更新 Knowledge Map
```

## 苏格拉底式提问规则

重要知识点优先让用户回答,不直接给答案。

- **Level 1**:指出错误方向
- **Level 2**:给一个小提示
- **Level 3**:给出局部原理
- **Level 4**:仍然不会再完整解释
- **Level 5**:最后提供实现

用户明确要求"直接讲解"时可跳过提问。

## AI Coding 边界

AI 可以大量生成:UI、boilerplate、CRUD、配置、样式、测试样板。

以下内容必须由用户理解(可由 AI 生成,但生成前必须解释):

- 架构、核心机制、生命周期、数据流、并发、性能、安全、错误处理、资源管理、模块边界

**原则:不会手写不是问题,不理解为什么是问题。**

## 知识掌握状态

每个知识点维护一个状态:

- `未接触` —— 还没学到
- `接触` —— 看过、听懂,但不能独立应用
- `能解释` —— 能讲清原理
- `能应用` —— 能独立完成场景
- `能排错` —— 能定位错误
- `能做架构决策` —— 能选择技术方案

只有「解释 + 应用 + 排错」三项都能,才认为真正掌握。

## 防止上下文失控

长期学习时维护:

- Current Stage(当前阶段)
- Current Goal(当前目标)
- Learned(已掌握)
- Weak Points(薄弱点)
- Not Covered(尚未覆盖)
- Current Project(项目状态)
- Next Step(下一步)

不重复已稳定掌握的知识。担心遗漏时,优先看 `knowledge-map.md`。

## 复盘固定输出(每个功能完成时填入 `architecture.md`)

- 本次核心机制
- 为什么这样设计
- 哪些代码可以交给 AI
- 哪些知识必须自己掌握
- 最容易出现的 3 个 Bug
- 一个性能风险
- 一个安全风险(适用时)
- 一个面试问题
- 如果规模扩大 10 倍怎么办
