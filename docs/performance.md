### Perf-001:大文件 Base64 —— Stream + Worker 是否真的解决「内存」与「卡顿」

**日期**:2026-10-08
**指标**:内存 / CPU / IO(阶段 4 核心性能实验)

**Baseline(基线)**:
```
阶段 2 实现(fs.readFile + Renderer 编码,限制 10MB):
- 内存占用 ≈ 文件大小 × (1 + 1.37) ≈ 文件大小 × 2.37
  (原始 Buffer + Base64 字符串同时在内存里)
- 10MB 文件 → ~24MB 峰值;100MB 文件 → ~237MB 峰值,不可接受
- 用户实测:105MB 文件被 10MB 限制拦下(报「文件过大」)
```

**瓶颈定位**:
- 怀疑点 1:**内存** —— fs.readFile 把整个文件读进内存,内存占用随文件大小线性增长(O(文件大小))
- 怀疑点 2:**CPU** —— Base64 编码是纯计算,跑在 Renderer 主线程会阻塞 UI(阶段 4 教学确认:异步 ≠ 不卡)

**假设**:
> ① Stream 分块读 + 逐块编码,内存占用从 O(文件大小) 降到 O(块大小),与文件大小**解耦**
> ② Worker 线程承载编码,主线程只做调度,界面在全程保持响应(不卡)

**修改**:
> 新增 `tool:big-base64` handler:`createReadStream(highWaterMark=3MB)` + `for await` 背压 + Worker 线程编码 + `finally { worker.terminate() }`;进度用 `webContents.send` 单向推送(100ms 节流);Renderer 通过 Preload 的 `onBase64Progress` 订阅进度并在 `useEffect` 清理中 unsubscribe。

**重新测量**:
```
用户实测(3.5MB / 105MB 级文件):
- 界面流畅度:全程无卡顿(拖动窗口、切换侧边栏均无阻塞)
- Base64 膨胀率:实测 1.333,与理论值 4/3 ≈ 1.3333 完全一致
- 处理完成后 Worker 线程正常退出,无残留线程
```

**比较**:
| 指标 | Baseline(阶段 2) | After(阶段 4) | 改善 |
|------|---------|-------|------|
| 内存复杂度 | O(文件大小) | O(块大小),与文件大小解耦 | 质的改善 |
| 可处理文件上限 | 10MB(硬限制) | 无上限(受磁盘与最终字符串长度限制) | 质的改善 |
| 界面响应 | 编码时卡死(主线程阻塞) | 全程流畅 | 质的改善 |
| 膨胀率 | 1.37(理论) | 1.333(实测,符合理论) | 符合预期 |

**结论**:
> **假设①②均验证成立。** 两个瓶颈确实是独立的两件事,必须用两套机制分别解决:
> - Stream 解决「内存」:块大小恒定 → 内存占用恒定
> - Worker 解决「CPU」:计算离开主线程 → 界面不会冻结
>
> **发现的遗留风险(重要)**:虽然分块读取控制了「处理过程」的内存,但**最终返回值仍是完整 Base64 字符串**。GB 级文件时,这个字符串本身(`base64Size` 个字符 ≈ 文件 ×1.37)会在「拼接」这一步重新撑爆内存 —— **分块省下的内存,在最后一步又还回去了**。真正的终极方案是「边编码边写文件」,让结果不经过内存。这是阶段 4 留下的技术债,已记入 architecture.md 的 ADR-005 后果栏。
>
> **另一个值得记录的工程教训**:阶段 4 注入的 Bug-003(块大小不是 3 的倍数)证明 —— **「指标健康」不等于「结果正确」**。Bug-003 场景下进度、膨胀率、输出长度全部正常,但数据静默损坏 71%。任何编码/序列化功能都必须有端到端往返测试,不能只看指标。
